# 21. Vite as the production build tool: client bundling, Worker build, and explicit environment selection

## Status

Accepted. Partially supersedes [ADR-0012](0012-client-modularization-factories-no-framework.md) — that ADR's title and Decision both name esbuild as the client bundler; this one replaces the bundler for both the client and (since it changes what deploys the Worker) the deploy pipeline. ADR-0012's own deeper decision — no frontend framework, factories over classes, a single Store addressed through named methods, a thin composition root — is untouched and still Accepted; nothing here revisits it.

## Context

The client had grown to 16 hand-rolled `esbuild` bundle invocations, one per page (`package.json`'s own `:build` scripts), each independently duplicating every shared module it imported — `climbing-tab-bar.js`, `admin-bar.js`, `calendar-date-picker.js`, `escape-html.js`, and others were each compiled into every bundle that touched them, not deduplicated. esbuild alone has no real cross-bundle code-splitting; this app's own `--external:./escape-html.js` convention was a hand-rolled attempt at exactly that, relying on every bundle landing flatly in the same output directory — brittle enough that it caused a real, previously-hit bug (#388) when a new component's relative import didn't match the flat layout it assumed.

Separately, `wrangler deploy` bundled `server/index.js` on its own, independently of the client build — a real `wrangler deploy --dry-run` measurement (2026-09-15) found the resulting Worker script at 2.2MB raw / 411KB gzip, containing hundreds of matches for unused Kysely SQL-dialect-adapter code that better-auth references defensively but this app never reaches (D1 is the only dialect ever used) — a static bundler can't tree-shake code only reached through runtime type-detection, not static imports.

A real spike (2026-09-15, throwaway branch, not merged) evaluated `@cloudflare/vite-plugin` against both problems together, deliberately, rather than adopting Vite for the client alone and discovering later that a deferred Worker-build question didn't fit the same tool. Findings:

- Vite/Rollup's multi-entry build genuinely code-splits: shared modules compile once, referenced by every entry that needs them, not duplicated. `log-app.js` dropped from 184KB to ~24KB (with shared chunks carrying the rest, downloaded once across all pages, not per-page).
- `@cloudflare/vite-plugin` is Cloudflare's own full-stack integration: with the plugin active for `vite build`, it builds the Worker script too, not just client assets, writing a `wrangler.json` redirect that `wrangler deploy`/`wrangler versions upload` detect and deploy directly from — Cloudflare's own documented behavior, not an incidental side effect.
- The plugin's own Worker build came in smaller than wrangler's existing one for equivalent code (1MB / 239KB gzip vs. wrangler's 2.2MB / 411KB gzip) — a real point in its favor, though the Kysely bloat itself is a separate, still-open problem either bundler has (tracked on its own issue, #776, left unfixed: the win doesn't clear the bar for aliasing a security-sensitive dependency's internals for a fix that only affects Worker-script size, not anything user-facing).
- A second, later empirical finding (2026-09-16, confirmed against Cloudflare's own docs) surfaced a real safety gap this project needed to design around, not just accept: the plugin selects which `wrangler.jsonc` named environment (`env.beta`, `env.preview`, the top-level/production config) a build targets via the `CLOUDFLARE_ENV` environment variable at **build** time — `wrangler deploy --env=X`/`wrangler versions upload --env X` have no effect on binding resolution once a build is Vite-produced. Confirmed live: omitting `CLOUDFLARE_ENV` entirely doesn't error at all, it silently falls back to the top-level config — which is production's real bindings. This is the exact incident class this project already hit once (`env.preview` silently inheriting production's D1 database before an explicit fix, `wrangler.jsonc`'s own `env.preview` comment) — a build tool that makes it possible to *not choose* an environment and get production anyway couldn't ship as designed.

## Decision

**`vite build` replaces esbuild for client bundling.** `vite.deploy.config.js`'s `environments.client.build.rollupOptions.input` lists all 16 `client/*-main.js` entries (shared with `vite.config.js`'s own dev-server config via `vite.entries.mjs`, avoiding a second hand-maintained copy of the same list — the exact class of drift that once left `scripts/dev.mjs`'s own watcher list silently missing `beta-gate`). Entry filenames stay stable and unhashed (`/logbook/<page>-app.js`) — [#760](https://github.com/ravendarque/climbing-logbook/issues/760)'s `views/*.njk` templates already reference them literally, and this migration needed zero template changes.

**`@cloudflare/vite-plugin` also builds the Worker**, in the same command, once its own environment-selection question (below) was resolved. `wrangler deploy`/`wrangler versions upload` no longer bundle `server/index.js` themselves at all — they detect the `wrangler.json` redirect the build writes and deploy straight from its output (`dist/climbing_logbook/`, `dist/client/`) instead.

**Every build that feeds a real deploy must set `CLOUDFLARE_ENV` explicitly — there is no implicit default.** Two layers enforce this, since the plugin itself only refuses an *unrecognized* environment name, not an absent one:

- `wrangler.jsonc` gains a real `env.production` section, mirroring `env.beta`/`env.preview`'s own already-established "explicit over inherited" convention (both already duplicate `vars`/`d1_databases` rather than relying on inheritance, after `env.preview` once silently inherited production's database that way). "Production" is now a validated environment name like the other two, not what you get by leaving the variable out.
- `scripts/require-cloudflare-env.mjs` runs before every deploy build (`pnpm run deploy:build`) and refuses to proceed unless `CLOUDFLARE_ENV` is exactly one of `production`/`beta`/`preview` — the check the tool itself doesn't provide.

`deploy.yml`/`promote.yml`/`preview.yml` each build immediately before their own deploy step, with `CLOUDFLARE_ENV` set to match (a single shared build step, like the old `client:build` this replaced, can only ever target one environment now). `--env=X` is kept on the actual `wrangler deploy`/`wrangler versions upload` calls too, as confirmed (not just documented) defense in depth — wrangler still throws if the flag disagrees with whatever environment the preceding build actually targeted.

**`wrangler dev` is deleted entirely** (`dev:raw` and the 16 esbuild `--watch` scripts it depended on). It survived only as inertia after an earlier decision ([#468](https://github.com/ravendarque/climbing-logbook/issues/468)) already made `vite dev` the default `pnpm dev` — `wrangler dev` has two confirmed bugs `vite dev` doesn't share (can't honor a `my.`-prefixed hostname at all; silently rewrites the request's own Host header in a way that breaks Better Auth's CSRF check). Cloudflare's own canonical scaffold for this plugin has no `wrangler dev` step anywhere. The e2e suite's `webServer` (`playwright.config.js`) moved from `wrangler dev` to `vite preview` (`CLOUDFLARE_ENV=preview`) — Cloudflare's own documented mechanism for "serve a real build in the Workers runtime before deploying."

**Client-only local dev/e2e and the real deploy build are two separate config files** (`vite.config.js`, dev-only; `vite.deploy.config.js`, the real build), not one file branching on `command`. `vite dev`'s `cloudflare()` plugin never builds the Worker (that's only its production-mode behavior); the deploy build needs `environments.client.build` scoping specifically to avoid its own client-entry config bleeding into the Worker's separate build (confirmed via the original spike — reproduced, then fixed). Keeping them apart means neither file has to reason about the other's concerns.

## Consequences

- One shared entry list (`vite.entries.mjs`) instead of the previous 16 esbuild scripts plus their own watch-mode duplicates — a new page needs one line added in one file, not a script pair plus three separate CI/dev-tooling copies kept in sync by hand (the exact class of bug `#391`/`#224` already both fixed once for this same "list of every page" problem, in the pre-Vite architecture).
- Every deploy build now costs one real Worker+client build instead of a lighter client-only step — a "direct" release (touching `migrations/`/`infra/`, deploying to both beta and production in the same job) now builds twice in `deploy.yml`, once per environment, since environment selection is build-time now. Accepted: correctness (never risking a silently-wrong environment) outweighs the extra CI minute this costs on the rare releases that hit both paths.
- The pre-existing Kysely SQL-dialect-adapter bundle bloat this migration's own spike surfaced is real but explicitly out of scope here — tracked on its own issue (#776), left unfixed: it's server-side only (doesn't affect what ships to the browser), and a real fix would mean aliasing a security-sensitive dependency's internals in a way that's fragile across version bumps, for a modest payoff.
- Whether `deploy.yml`/`promote.yml` should build once and share the resulting artifact rather than each rebuilding independently — the question this migration made newly answerable, since a Vite-built Worker's `dist/` output is now a genuine, coherent "the whole deployable app" the way the previous wrangler-bundled Worker plus a separately-built `public/` never quite was — remains open, tracked on its own issue (#772), deliberately not decided here.
- Dev-mode HMR (Vite's own module graph serving `client/*-main.js` on demand, with a small `configureServer` middleware keeping `views/*.njk` templates completely unaware of dev vs. prod) replaced the previous ~17-process `concurrently`-orchestrated esbuild-watch tree with Vite's own dev server — real HMR (confirmed via a live edit appearing on screen with zero manual reload), not just a faster rebuild loop.
