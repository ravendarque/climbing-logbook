# 23. Instant shell, decoupled content loading, and a shell-level sync/offline indicator

## Status

Accepted

## Context

This app is built for climbers at the crag on slow, unreliable connections, and already has an offline-first local cache (`localStorage`) for entries/places/locations (`client/store.js`, [ADR-0019](0019-local-first-sync-chunked-initial-load-and-delta.md)). Despite that cache existing, every owner-facing page's *reveal* was still gated behind full network round-trips. Raven reported four concrete symptoms: a logbook "flash" (content loads, disappears, then reappears), a slow-to-appear tab bar, a long wait before any UI appears, and default "no data" messages shown while real cached data already existed.

A 2026-09-14 investigation (recorded in full in [#762](https://github.com/ravendarque/climbing-logbook/issues/762)'s own issue body and `docs/superpowers/specs/2026-09-14-perceived-performance-boot-architecture-design.md`) confirmed real, specific causes shared across all 9 owner-only composition roots that render `<climbing-tab-bar>` (`client/log-main.js`, `client/map-main.js`, `client/performance-{hub,pyramid,gap,grades,injury,rpe,strengths}-main.js`):

- `tabBar.markReady()` — which gates the tab bar's entire first paint — was the last line of every `boot()`, called only after every network call resolved.
- `admin-auth.js`'s settings (`athleteMode`/`logbookPublic`/`betaOptIn`/`persistedDiscipline`) had no `localStorage` cache at all — every page restarted from an in-memory default and re-fetched fresh, even on a device that already knew the answer.
- `store.loadEntriesFromCache()` never called `notify()` — cached entries loaded into memory silently and only reached the DOM once some *other*, network-gated mutation happened to fire `notify()` later.
- `/map`'s counts cache was write-only during normal operation — always awaiting the network fetch first and reading the cache only as a failure fallback, never as an instant first paint.
- Performance Insights pages (`pyramid`/`trends`/`gap`/`rpe`/`injury`/`strengths`/`hub`/`grades`) deliberately have no client-side report cache at all ([ADR-0018](0018-server-side-aggregation-for-derived-views.md): a stale or unavailable aggregate must never be silently recomputed client-side) — correct, and unchanged by this work — but their page *shell* was needlessly coupled to that same online-only gate, so the whole page waited even though the shell chrome has nothing to do with report availability.

None of the existing ADRs cover this. [ADR-0017](0017-connectivity-first-scoped-to-owner-write-path.md) decides *which pages* get connectivity resilience at all, not how a page's own shell and content phases sequence against each other. [ADR-0018](0018-server-side-aggregation-for-derived-views.md) and [ADR-0019](0019-local-first-sync-chunked-initial-load-and-delta.md) each govern one page family's own data-fetch mechanism (Performance Insights' online-only aggregates; `/log`'s chunked sync) and are explicitly **not** touched by this change (see Consequences) — neither speaks to the cross-cutting question of when the surrounding tab bar and nav chrome may render.

## Decision

**Every owner page's shell (tab bar + header chrome) renders instantly from `localStorage`, with zero network dependency — content renders per whatever policy already governs that specific data, decoupled from the shell.** No new "boot orchestrator" module was needed: `store.subscribe(render)` already meant every `notify()` call drove a full re-render through `syncAdminBar()` ([client/admin-bar.js](../../../client/admin-bar.js)); the fix was narrower — feed that existing plumbing accurate optimistic state as early as possible, not add a parallel mechanism.

Concretely:

- **`tabBar.markReady()` moved into `syncAdminBar()` itself** ([client/admin-bar.js:63](../../../client/admin-bar.js)), called unconditionally on every render rather than once at the end of each composition root's own `boot()`. It relies on `<climbing-tab-bar>`'s own pre-existing idempotent `markReady()` (a no-op after the first real call) — the tab bar becomes visible the moment the *first* render happens, whichever data seeded it, and no composition root has to remember its own `// #605`-style call site any more.
- **`resolveActiveType()` split into a synchronous half and an async half** (`client/admin-auth.js`): `setInitialActiveType()` runs synchronously at the very top of every `boot()`, before any network call starts, preferring a cached persisted discipline over the has-entries heuristic when one exists; `reconcileActiveType(sessionPromise, settingsPromise)` keeps the original await-then-maybe-override behavior for the rare case a device's cached discipline is stale relative to the server.
- **A new settings cache, `logbook_settings_cache`** (`admin-auth.js`), mirrors `store.js`'s existing `ENTRIES_CACHE_KEY`/`PLACES_CACHE_KEY`/`LOCATIONS_CACHE_KEY` convention: written on every successful `fetchSettings()`, read synchronously at construction time to seed initial in-memory values, and used as `fetchSettings()`'s own failure fallback instead of silently keeping an in-memory default.
- **`checkSession()` reads its existing login hint synchronously and calls `store.setLoggedIn()` before the network call starts**, not only in the failure branch as before — a slow-but-eventually-successful session check no longer blocks the shell's first paint on its own round trip.
- **`store.loadEntriesFromCache()` now calls `notify()`** ([client/store.js:129-134](../../../client/store.js)) — cached entries reach the DOM the instant they load, not on whatever later network-gated mutation happens to fire next.
- **`/map`'s `loadMapCounts()` became true stale-while-revalidate** — the cache is read and applied first, unconditionally, before the network fetch starts; the fetch still runs and silently corrects the view if the real value differs.
- **A new shared "background activity" counter drives a shell-level sync/offline icon**, `client/sync-status-icon.js`'s `createSyncStatusIcon()` — a small factory (`track(promise)` increments an in-flight counter before a background reconcile call, decrements in its `finally`) instantiated once per composition root and wired to `checkSession()`/`fetchSettings()`/`/log`'s places-and-locations refresh/`offline-sync.js`'s `pullDeltas()`. It renders through `<climbing-page-header>`'s `setSyncState("idle"|"working"|"offline")`, is deliberately a *separate* concept from `offline-sync.js`'s pre-existing `sync-btn` (queued local writes not yet pushed), and deliberately excludes each page's own primary-content fetch (map counts, Performance Insights report data) — those already have their own appropriate loading/offline treatment; this icon communicates the shell's own reconcile state, not page content state.

## Consequences

- Every one of the 4 reported symptoms is addressed by making the shell's own first paint depend only on synchronous, already-cached state — no bespoke "flash-free swap" machinery was needed, because the existing `subscribe`/`notify`/`render()` reactivity already re-renders correctly once real network data lands.
- **No change to [ADR-0018](0018-server-side-aggregation-for-derived-views.md)** — Performance Insights pages still have zero client-side report cache and zero client recomputation; only their *shell* was decoupled from that page's report fetch.
- **No change to [ADR-0019](0019-local-first-sync-chunked-initial-load-and-delta.md)** — `/sync`'s own dedicated chunked-sync progress UI is untouched, and the new shell-level sync/offline icon is explicitly suppressed on `/sync` itself to avoid two different-looking "syncing" signals on the one page whose entire job is already showing sync progress.
- `entriesTable.loading` ([client/components/climbing-entries-table.js](../../../client/components/climbing-entries-table.js)) stays a distinct, narrower concept from the page-shell reveal — it still governs `<climbing-entries-table>`'s own "Loading…" vs "Nothing to show" text — but because entries are now visible immediately whenever a cache exists, it is only meaningfully `true` for a demo visitor or a genuinely cache-less first-ever load.
- Bundle-size/code-splitting work was deliberately kept out of scope here and landed separately under epic #758 ([ADR-0021](0021-vite-for-production-build-client-and-worker.md)); this epic's own boot-sequencing changes were sequenced to land *before* that work, giving it a stable, already-correct runtime target to verify bundling equivalence against.
- `/account*`, `/profile`, and `/sync` composition roots were confirmed, not assumed, not to share this bug — each already used `Promise.all` correctly or (for `/sync`) has a genuinely different, already-appropriate dedicated progress flow — and were left untouched.
